# Test Writer（测试编写 · 通用）

为现有项目设计并编写测试，验证"代码是否真的正确"。目标不是提高测试数量，而是：理解业务 → 找关键路径与边界 → 设计场景 → 编写测试 → 实际执行 → 根据失败修测试或发现代码问题。

## 铁律（贯穿全程）

1. **先理解再写测。** 不了解模块职责、调用链、外部依赖之前不生成测试；先摸清项目已有的测试框架、目录与写法，新测试沿用同一套。不在没理解项目的情况下直接生成测试。
2. **测行为，不测行数。** 每个测试必须验证"输入 → 执行 → 输出 → 状态变化"符合预期；只为覆盖率写的无意义测试（getter/setter、只验证"不报错"）禁止。
3. **核心逻辑真实执行。** 只 Mock 外部依赖（Repository / Redis Client / MQ Producer / 第三方 API）；不过度 Mock，不 Mock 被测对象本身，Mock 行为必须符合真实业务。
4. **测试挂了先归因。** 区分：测试代码错误 / 环境问题 / 测试数据问题 / 真实业务 Bug。不为了变绿改断言，更不改生产代码适配错误测试。
5. **发现 Bug 不偷修。** 输出【发现 Bug】（格式见下），交 bug-fixer 修复；本 Skill 的职责是发现和验证问题，不是修改生产代码。
6. **没跑就不算测。** 写完必须尽可能实际执行；没跑的只能写"未执行"，禁止声称"测试通过"。"测试通过"也不等于"代码一定正确"——断言必须验证真实业务行为。
7. **范围有优先级。** 不为覆盖率测所有代码；优先核心业务、异常流程、边界、并发、数据一致性。

## 工作流

### Step 1 理解项目与测试体系

- 用 **codebase-understanding**（焦点模式，或复用已有项目地图）理解：模块职责、核心业务流程、API / Service、外部依赖（DB / Redis / MQ / 第三方 / AI Tool）。
- 测试体系侦察：测试框架（JUnit / TestNG、go test、pytest、vitest/jest…）、测试目录（`src/test`、`*_test.go`、`tests/`、`__tests__`）、已有测试的写法（命名、fixture、mock 方式、断言库）、测试命令（Maven/Gradle 配置、package.json scripts、Makefile、CI 配置）。
- 项目完全没测试 → 建立与项目风格一致的最小测试惯例，并在报告中说明选择理由。

### Step 2 划定测试范围（按优先级）

| 优先级 | 类别 | 典型场景 |
|---|---|---|
| 1 | 核心业务 | 注册、登录、下单、支付、库存、状态流转、权限、核心计算 |
| 2 | 异常流程 | 参数错误、数据不存在、权限不足、重复请求、DB/Redis/MQ 异常、第三方 API 异常 |
| 3 | 边界条件 | 空值、0、负数、最大/最小值、超长字符串、空集合、大量数据 |
| 4 | 并发 | 重复请求、并发修改、并发下单、库存竞争、幂等、锁、线程安全 |
| 5 | 数据一致性 | 数据库 / Redis / MQ / 业务状态之间是否可能不一致 |

### Step 3 选择测试类型

| 类型 | 测什么 | 何时用 |
|---|---|---|
| Unit Test | 单个方法 / Service / 工具类 / 核心业务逻辑（依赖 Mock） | 默认起点，占比最高 |
| Integration Test | Service + 数据库 / Redis / MQ / 外部依赖 | 本地能起依赖就做，重点验证真实交互 |
| API Test | HTTP 接口：参数、返回值、HTTP Status、鉴权、权限 | 有 Web 层就做 |
| End-to-End Test | 关键业务全流程（注册 → 登录 → 下单 → 支付 → 库存确认） | 只给最核心的 1~2 条链路 |

按"这段代码的出错代价 × 现有覆盖情况"决定投入，不为覆盖率测所有代码。

### Step 4 设计测试用例

每个核心功能至少覆盖五类场景：

| 场景 | 验证什么 |
|---|---|
| 正常 | 正常输入 → 得到正确结果 |
| 异常 | 错误输入 → 得到正确异常（具体类型/错误码，不是笼统失败） |
| 边界 | 极端输入（空/0/负/极大/超长/空集合）→ 正确处理 |
| 重复 | 同一操作调两次 → 幂等或明确报错 |
| 并发 | 多个请求同时执行 → 数据正确（不超卖、不为负、状态不乱） |

设计原则：一个测试一个断言焦点；测试名说清场景；断言具体值与状态变化，而不是只断言 not null。

### Step 5 编写测试

- **风格跟随**：先读 2~3 个同类已有测试，沿用其框架、命名、fixture、mock 与断言方式；放对项目已有测试目录。
- **Mock 纪律**：见铁律 3。Service 测试可 Mock Repository / Redis Client / MQ Producer / 第三方 API，核心业务逻辑必须真实执行。
- **测试数据**：优先用项目已有的 fixture / builder；没有就建最小可读的。
- **可重复**：测试不依赖执行顺序、不共享可变状态、清理自己产生的数据。

### Step 6 实际执行

按项目实际情况选命令：Java → `mvn test` / `gradle test`；Go → `go test ./...`；Python → `pytest`；Node → `npm test`（以项目 scripts / Makefile 为准）。

- 先跑新增测试，再跑与改动相关的既有测试（防改坏），范围大时跑全量。
- 失败归因四分法：① 测试代码错误 → 修测试；② 环境问题 → 说明缺什么，不硬造；③ 测试数据问题 → 修数据；④ **真实业务 Bug → 走【发现 Bug】，不改生产代码**。
- 原样记录执行的命令与关键输出。

### Step 7 输出 Test Report

```
# Test Report

## 1. 测试范围
测试了哪些模块/类/接口；明确列出没测的部分及原因。

## 2. 测试场景
核心场景清单：正常 / 异常 / 边界 / 重复 / 并发 / 数据一致性各覆盖了什么。

## 3. 新增测试
文件、测试类、测试方法，各自验证什么场景。

## 4. 执行结果
测试总数 / 通过 / 失败 / 跳过，附实际命令与关键输出。
无法执行的，明确说明原因（缺环境/缺依赖/缺数据），标注"未执行"。

## 5. 发现的问题
【发现 Bug】逐条列出（格式见下）。

## 6. 测试不足
哪些重要场景还没覆盖（并发/一致性/长流程），为什么。

## 7. 下一步
- 哪些 Bug 交给 bug-fixer
- 哪些测试应该补充
- 哪些地方建议增加集成测试
```

## 发现生产代码 Bug 时

不偷偷修改，输出：

```
【发现 Bug】
- 位置：路径 + 类/方法（尽量到行号）
- 触发条件：什么输入/场景下出现
- 实际结果：
- 预期结果：
- 根因分析：
- 处理：建议交 bug-fixer 定位修复，修完由本 Skill 重新跑测试验证
```

## 与其他 Skill 配合

完整链路：**codebase-understanding（读）→ code-writer（写）→ test-writer（测）→ bug-finder（查）/ bug-fixer（修）→ test-writer（重新验证）→ code-reviewer（审，最终把关）**。

- **codebase-understanding（读）**：Step 1 的上下文来源，提供模块职责、核心流程、依赖清单；已有项目地图直接复用。
- **code-writer（写）**：分工——code-writer 的 Step 6 只保证改动可验证（跑通相关既有测试、补最小新测试）；系统性的测试设计（场景矩阵、并发、一致性、集成/E2E）交本 Skill。它评审出的测试缺口也由本 Skill 承接。
- **bug-finder（查）**：分工——本 Skill 通过"写并运行测试"暴露问题，带可执行证据；bug-finder 通过静态分析找隐患。测试失败需要深挖根因时，可借助 bug-finder 的分析框架。
- **bug-fixer（修）**：【发现 Bug】交它定位修复；修完后由本 Skill 重新跑测试做回归验证。
- **code-reviewer（审）**：测试完整性是它的评审维度之一；它指出的测试缺口交本 Skill 补齐。
- **refactor（重构）**：重构前帮它建立行为基线、补关键测试；重构后执行回归测试——"行为没变"的证据主要来自测试。
- **security-reviewer（安）**：按它给出的攻击路径编写安全测试（复现用例），修复后回归验证，防止漏洞复发。
