# Refactor（代码重构 · 通用）

在**不改变业务行为**的前提下优化代码结构：理解现有代码 → 找出真正的结构问题 → 制定最小风险方案 → 重构 → 测试 → 确认业务行为没有改变。重构的目的是降低后续修改成本，不是让代码"看起来高级"。

## 铁律（贯穿全程）

1. **行为一致是底线。** 默认情况下输入相同 → 输出相同，异常行为也尽量保持一致；除非用户明确要求修改业务行为。偷偷改变业务逻辑、API、数据库是重构的大忌。
2. **没有足够上下文不动手。** 不理解调用方、依赖方、业务流程、外部依赖之前不重构；没建立行为基线不声称"重构安全"。
3. **有明确收益才重构。** 判断标准是"降低修改成本、消除实际维护痛苦"，不是"代码不漂亮"。收益低 → 直接说"当前不建议重构"，这是有价值的结论，不是失职。
4. **小步走。** 小范围修改 → 编译 → 测试 → 再继续；不一次修改几十个模块。
5. **最小修改。** 不顺便改命名、换框架、升级依赖、改数据库、改 API——除非这些变化本来就属于重构目标。
6. **不过度设计。** 不为了使用 Factory / Strategy / Template / Observer / DDD / CQRS 而强行引入；只有实际解决问题时才用，并说明它解决了什么。
7. **发现问题不顺手修。** 重构中发现 Bug → 输出【发现 Bug】交 bug-fixer；发现无关坏味道 → 记录进报告，不顺手改。
8. **如实汇报。** 测试失败如实说并归因；行为有任何变化必须在报告里明确指出，不允许"应该没变"。

## 工作流

### Step 1 理解上下文（重构前必须做完）

- 用 **codebase-understanding**（焦点模式，或复用已有项目地图）理解项目结构、模块职责、相关业务流程。
- 对目标代码摸清四件事：**谁在调它**（调用方）、**它依赖谁**（依赖方）、**属于哪条业务流程**、**涉及哪些外部依赖**（DB/Redis/MQ/API/第三方/AI Tool）。
- 检查现有测试：有哪些、覆盖什么、能不能跑。
- 上下文不足 → 不重构，先说明缺什么。

### Step 2 判断是否真的需要重构

不看到代码不漂亮就重构。只有存在明显收益才建议，例如：

- 修改成本高：加一个小功能要改一大片。
- 重复代码导致维护困难：同逻辑多处拷贝，改一处漏三处。
- 一个类承担多个明显不同的职责。
- 一个方法过于复杂，难以理解。
- 模块之间存在不合理耦合 / 循环依赖。
- 测试非常困难（无法单测、要起一堆依赖）。
- 扩展功能需要频繁修改大量代码。
- 存在明确的性能或稳定性问题。

**当前代码虽然不够漂亮，但没有明显问题 → 明确告诉用户"当前不建议重构"。**

### Step 3 建立行为基线（重构前最重要的一步）

- 现有测试全部跑一遍并记录结果（通过/失败各多少）。
- 能跑的做冒烟：核心 API 正常、核心业务流程正常、数据库/Redis/MQ 行为正常。
- **项目没有测试 → 至少明确记录当前代码的关键行为**（输入 → 输出、状态变化、异常行为），写进方案，重构后逐条对比。
- 既有测试里本来就挂的 → 记录下来，不算在重构账上。

### Step 4 制定重构方案（对用户可见）

动手前给出：

```
【当前问题】具体是什么（带 路径:行号）
【重构目标】希望改善什么（可衡量，如"下单逻辑从 3 处收敛到 1 处"）
【重构方案】怎么做、分几步
【修改范围】哪些文件/类/方法/模块会变化
【风险】可能影响什么
【验证方案】如何证明业务行为没有改变（基线对比 + 测试清单）
```

按重构类型决定是否等确认：

| 级别 | 典型动作 | 流程 |
|---|---|---|
| 小范围 | 提取方法/变量、删除重复代码、简化条件判断、优化命名、简化复杂逻辑 | 方案给出后直接执行 |
| 类级别 | 拆分类、调整职责、降低耦合、优化依赖关系 | 方案给出后直接执行，用户可打断 |
| 模块级别 | 调整模块职责、调整依赖关系、拆分公共代码、消除循环依赖 | 方案给出后等用户确认 |
| 架构级别 | 调整服务边界/领域边界/数据访问方式/消息处理架构 | **必须先给详细方案，不允许直接大规模修改** |

### Step 5 小步执行

- 每一步只做一类变换（如只提取方法、只移动类），改完立即编译 + 跑相关测试，绿了再继续。
- 每步保持可回退；发现行为对不上基线，立即停下查明原因，不带病前进。
- 遵循项目现有风格；公共接口、序列化字段、反射/配置引用的类名与方法名是隐式契约，默认不动，必须动时在方案中声明。

### Step 6 重构中重点检查

按项目实际用到的技术域：

| 域 | 检查项 |
|---|---|
| Java | Spring Bean 依赖方向、AOP（自调用失效？）、事务（重构后事务边界还在吗）、线程安全、ThreadLocal、线程池、Stream 滥用、Optional 滥用、异常体系 |
| Go | interface 是否过度抽象、package 职责、error handling（有没有被吞）、goroutine 生命周期、channel、context 传递、mutex、package 依赖方向 |
| 数据库 | SQL 与 Mapper/Repository、事务边界、数据访问重复、N+1、查询性能（重构不能引入慢查询） |
| Redis / MQ | 缓存逻辑、消息处理、幂等、重试、状态一致性（重构不能破坏一致性保障） |
| AI | Prompt 管理、Tool 抽象、Agent Loop、Context 管理、Token 管理、Provider 抽象、RAG Pipeline、错误处理 |

### Step 7 重构后验证

尽可能执行：编译 → 单元测试 → 集成测试 → API 测试 → 静态检查 → 必要的手动验证；并逐条对比 Step 3 的行为基线。

测试失败先归因：① 重构引入的问题 → 修（这是我的责任）；② 原项目已有问题 → 记录，不顺手大修；③ 测试代码问题 → 说明理由，经确认才改；④ 环境问题 → 说明缺什么。**不简单修改测试让它通过。**

### Step 8 输出 Refactor Report

```
# Refactor Report

## 1. 重构原因
为什么需要重构，收益是什么。

## 2. 重构前
原来的问题（带 路径:行号 与证据）。

## 3. 重构方案
采用了什么方案，分几步，每步的变换类型。

## 4. 修改内容
文件 / 类 / 方法 / 模块清单 + 核心变化。

## 5. 行为变化
- 哪些业务行为没有改变（基于基线对比）
- 是否存在 API 变化 / 数据库变化 / 配置变化
存在任何行为变化必须明确指出，不允许"应该没变"。

## 6. 验证结果
编译 / 单测 / 集成 / API / 静态检查 / 手动验证，哪些通过、哪些失败（原样给命令与关键输出）。
没实际执行的，明确标注"未执行"。

## 7. 风险
剩余风险、发现但未处理的问题（带 路径:行号）。

## 8. 后续建议
是否还有必要继续重构、建议的顺序。
```

## 与其他 Skill 配合

完整链路：**codebase-understanding（读）→ code-reviewer（审，发现结构问题）→ refactor（方案 + 小步执行）→ test-writer（补/执行测试）→ bug-finder（查）→ bug-fixer（修）→ code-reviewer（最终 review）**。形成：理解 → Review → 重构 → 测试 → 找 Bug → 修复 → Review。

- **codebase-understanding（读）**：Step 1 的上下文来源；已有项目地图直接复用坐标。
- **code-reviewer（审）**：结构问题（重复/职责混乱/耦合/难测试）通常由它指出并定级；确认值得改的交本 Skill 制定方案并执行。它只审不改。
- **architecture-reviewer（架）**：服务/模块级拆分与系统级边界问题交它；本 Skill 管代码级（类/方法）的结构重构。
- **code-writer（写）**：分工——新功能/常规改动走 code-writer；以"行为不变"为前提的纯结构优化走本 Skill。需求本身要求改行为的，那是 code-writer 的活。
- **test-writer（测）**：重构前帮它建立行为基线、补关键测试；重构后执行回归测试——"行为没变"的证据主要来自测试。
- **bug-finder（查）/ bug-fixer（修）**：重构完成后可跑一轮 bug-finder 确认没引入新问题；发现 Bug 交 bug-fixer 修复，修完回归。
