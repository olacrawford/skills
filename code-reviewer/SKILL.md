# Code Reviewer（代码审查 · 通用）

对"准备进入真实项目的代码"做系统性工程质量评审：不只找 Bug，而是回答三个问题——**能不能合入、上线后会不会出事、以后好不好维护**。只审不改，产出报告与修改优先级。

## 铁律（贯穿全程）

1. **先上下文，后结论。** 不孤立看一个方法就下结论；评审前必须搞清模块职责、调用链、上下游与外部依赖（DB/Redis/MQ/第三方）。
2. **工程价值优先。** 只报真实工程问题；命名风格、空格、注释数量、大括号风格等低价值问题不占篇幅。判断基准是"会不会出事、好不好维护"，不是个人偏好。
3. **不凑数。** 发现 2 个问题就报 2 个，不硬凑 20 个；代码好的地方明确写 GOOD——评审的价值在准确，不在数量。
4. **不猜测。** 说不清触发条件或影响的，进「需要进一步确认」；安全问题必须给出实际攻击路径，否则不定级。
5. **只审不改。** 不修改任何业务代码。发现 Bug 交 bug-fixer，重构交 refactor，设计问题交 code-writer，测试缺口记入报告。
6. **说清后果。** 每个问题必须写"为什么是问题 + 不修的后果"；禁止只说"这里可以优化"。
7. **不重复劳动。** 用户已跑过 bug-finder 的，引用其结论，不重复输出同样的 Bug；本次评审聚焦它没覆盖的维度。

## 评审模式

| 模式 | 触发 | 做法 |
|---|---|---|
| 改动评审（默认） | 用户给 diff / PR / MR / 某次改动 | 聚焦改动文件 + 直接影响面（调用方、数据、配置），完整走 Step 2-9 |
| 模块评审 | 指定某个模块 | 该模块全量 + 与外部的接缝（入参出参、共享数据、消息） |
| 全项目评审 | "整体 review 一遍 / 上线前把关" | 按核心业务链路逐模块评审；大项目优先核心链路，边缘模块只扫结构 |

## 工作流

### Step 1 理解上下文

- 陌生项目/模块 → 调用 **codebase-understanding**（焦点模式）拿：模块职责、关键调用链、外部依赖；已有项目地图或 bug-finder 报告 → 直接复用坐标与结论。
- 改动评审先看 diff 与关联文件：这个改动动了谁、谁在调它、共享了什么数据。
- 明确记录评审范围与**没评审的部分**（写进报告第 7 节）。

### Step 2 正确性

业务逻辑、状态流转、参数处理、返回值、异常情况、边界条件、空值、重复请求、重试、超时、并发调用。发现明确 Bug 照常报告（用本 Skill 的问题卡格式），但与 bug-finder 已有结论交叉核对，不重复展开同一问题。

### Step 3 代码设计

- 单一职责：方法/类职责是否过重、混乱。
- 重复代码：同一段逻辑多处拷贝（改一处漏三处的那种）。
- 过度抽象 / 过度设计：小改动上大模式、只有单实现的接口、无意义的间接层。
- 架构一致性：是否违反项目已有分层与架构（该在 service 的写进 controller、越层调用、绕过既有公共组件）。
- 耦合与可测性：难以单测、难以扩展的点。

判断基准是**项目自己**的架构与惯例，不是教科书；不为"设计模式"强行重构——一个 if 能解决的不上策略模式。系统级架构问题（模块边界/服务拆分/一致性/可靠性/扩展性）超出代码评审范围，交 **architecture-reviewer**。

### Step 4 性能

必须以实际代码为证据，有明确触发路径才报：

- 数据库：SQL 写法、索引是否命中、**N+1 查询**、循环内查库/调接口、大结果集无分页、事务过长。
- 资源：不必要的对象创建（循环内）、IO 未复用/未关闭、每请求建连接。
- 中间件：Redis 用法（大 Key、热 Key、慢命令）、MQ（吞吐、堆积风险）。
- 并发设施：锁粒度、线程池配置（核心数/队列/拒绝策略）。
- AI：Agent Tool 调用次数、LLM API 调用方式、Token 消耗（循环拼 Prompt、上下文无限增长）。

"理论上可能慢"不是问题；"循环里每次查库、列表页每行发一次 SQL"才是。

### Step 5 并发

核心问题只有一个：**"两个请求同时进来会发生什么？"** 对每个共享状态、非幂等写操作过一遍双请求场景。

检查项：共享变量、线程安全、锁（synchronized / 分布式锁）的正确性与粒度、volatile / CAS / Atomic / ConcurrentHashMap 的误用、ThreadLocal（用完没清理？线程池复用串数据？）、ThreadPool 配置、Goroutine 泄漏、Channel 关闭、数据库并发更新（check-then-act、丢更新）、Redis 分布式锁（过期时间、误删他人锁、不可重入）。

### Step 6 数据一致性

对每条跨存储写路径（数据库 → Redis → MQ → 业务状态），逐个检查"成功一半"：

- DB 成功、Redis 失败 → 脏缓存/不一致，有无补偿或过期兜底。
- Redis 成功、DB 失败 → 缓存里是不存在/错误的数据。
- DB 成功、MQ 发送失败 → 下游漏消息，有无重试/本地消息表。
- MQ 重复消费 → 消费逻辑幂等吗。
- 状态重复修改 → 重复请求/重试下状态会被改两次吗。
- 事务范围错误 → 该在一个事务的被拆开；事务里做 RPC/发消息（长事务）。
- 缓存脏数据 → 更新顺序（先 DB 后缓存？删缓存还是改缓存？）。

### Step 7 安全

SQL 注入、XSS、CSRF、越权（水平/垂直——能不能访问别人的数据）、鉴权遗漏、JWT（密钥、过期、算法）、敏感信息泄露（日志打密码/Token/手机号明文）、文件上传（类型校验、路径穿越）、SSRF、命令执行、API Key 泄露（硬编码/日志/前端暴露）。

AI 项目追加：Prompt Injection（用户输入直接拼 Prompt？）、Tool 权限（Agent 能调哪些工具、有没有白名单）、AI 数据泄露（检索内容/对话历史带敏感数据出去）。

**硬规则：报告安全问题必须写清实际攻击路径或触发条件**——谁能、从哪个入口、怎么利用、造成什么后果。给不出路径的进「需要进一步确认」。系统性、攻击者视角的安全审查（攻击面/渗透路径）交 **security-reviewer**。

### Step 8 AI / Agent / RAG / MCP 专项（项目涉及才做）

Prompt 设计（是否稳定可测、有无版本管理）、Prompt Injection、Tool 参数校验、Agent 无限循环（最大轮数/退出条件）、Agent 状态管理、Token 消耗与成本、Context 长度限制、LLM 超时与重试、Rate Limit、RAG 检索质量（召回不准时的兜底）、Embedding 与向量库使用、数据来源可信度、敏感数据、模型输出可信度（直接落库/直接执行？有无校验）。

### Step 9 测试完整性与工程规范

- 测试：核心路径与边界有没有测试；本次改动有没有对应测试；测试在测行为还是只测 mock 调用链；实际跑一遍是否通过。
- 工程规范（只报造成实际维护成本的）：配置硬编码（URL/密钥/魔法值）、日志无法定位问题（没 TraceId/没上下文）、错误处理不统一、注释与实现不一致、公共组件被绕过。

### Step 10 定级

| 级别 | 定义 |
|---|---|
| P0 | 严重：数据损坏、安全漏洞、系统不可用级别，合入即出事 |
| P1 | 高：主流程大概率出错或产生实际损失，合入前必须修 |
| P2 | 中：特定条件下出问题，或明显设计缺陷，尽快修 |
| P3 | 低：改进建议，择机处理 |
| GOOD | 值得保留的设计：说明好在哪，值得其他模块借鉴 |

定级方法：触发概率 × 影响后果。说不出触发条件的不定级，放「需要进一步确认」。

## 单个问题输出格式

```
【等级】P0 / P1 / P2 / P3 / GOOD
【位置】文件路径 + 类/方法（尽量到行号）
【问题】具体说明
【原因】为什么这是问题
【影响】不修会产生什么实际后果
【建议】怎么改（方案级别即可）
【优先级】建议现在修 / 合入前修 / 择机修
```

硬规则：禁止只说"这里可以优化"——必须说清为什么要优化、不优化会产生什么后果。

## 最终报告

```
# Code Review Report

## 1. 总体评价
几句话：整体质量、**是否建议合入/上线**、最担心的方向。

## 2. P0 / P1
最严重的问题，每条一张问题卡，按影响排序。

## 3. P2
中等问题，每条一张问题卡。

## 4. P3
低优先级改进，可合并为简短列表。

## 5. GOOD
值得保留的设计，说明好在哪。

## 6. 最优先修改的 5 个问题
按收益/风险排序，说明为什么优先。

## 7. Review 范围
实际检查了哪些模块、文件、维度；**明确列出没检查的部分及原因**。

## 8. 下一步建议
- 修改什么（明确交 bug-fixer / code-writer）
- 测试什么（测试缺口，交 test-writer）
- 是否需要重构、是否需要补测试
- 需要进一步确认的问题 + 需要什么信息
```

## 与其他 Skill 配合

标准链路：**codebase-understanding（读）→ code-writer（写）→ bug-finder（查）→ bug-fixer（修）→ test-writer（测）→ code-reviewer（审，最终质量把关）**。

- **codebase-understanding（读）**：评审前的上下文来源（Step 1）；已有项目地图直接复用坐标。
- **bug-finder（查）**：分工——bug-finder 专注"运行时会不会出 Bug"的单点深挖；本 Skill 做全维度工程质量评审（设计/性能/安全/测试/规范 + GOOD）。同一批代码已跑过 bug-finder 的，引用其结论不重复；本 Skill 发现新的明确 Bug → 交 bug-fixer。
- **bug-fixer（修）**：评审发现的明确 Bug，由它定位根因并修复。
- **refactor（重构）**：确认值得改的结构问题（重复/职责混乱/耦合/难测试），带上方案级建议交它制定方案并执行；本 Skill 只审不改。
- **code-writer（写）**：需要新增功能/常规改动才能解决的问题，交它执行。
- **performance（能）**：评审只能报"有明确代码证据"的单点性能问题；系统性的性能测量、定位与优化交它做。
- **security-reviewer（安）**：评审只报"有明确攻击路径"的单点安全问题；系统性、攻击者视角的安全审查交它做。
- **architecture-reviewer（架）**：代码评审只能看到文件内的设计问题；模块边界、服务拆分、一致性、可靠性等系统级问题交它做。
- **test-writer（测）**：评审指出的测试缺口交它补测试；它跑测试发现的新 Bug 回流给 bug-fixer。
