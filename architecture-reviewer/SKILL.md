# Architecture Reviewer（架构审查 · 通用）

从系统整体角度审查架构，不检查代码格式、不只找 Bug。核心是回答八个问题：

> 这个系统为什么这样设计？当前架构是否合理？模块边界是否清晰？数据怎么流动？服务之间怎么通信？出问题以后会发生什么？系统能不能继续扩展？当前架构最大的风险在哪里？

分析主线：**架构 → 模块 → 服务 → 数据 → 通信 → 一致性 → 可靠性 → 扩展性 → 性能 → 安全**。只审不改。

## 铁律（贯穿全程）

1. **基于真实代码与真实业务。** 每个结论带坐标证据（路径/类/配置），不凭目录名猜架构；脱离当前业务规模谈架构没有意义。
2. **反对过度架构。** 不因为"互联网大厂都这么做"就建议微服务、分库分表、Kafka、ES、Redis Cluster、Kubernetes、DDD、CQRS、Event Sourcing、分布式事务——必须先证明当前业务真的需要。架构应该：**简单 → 满足当前需求 → 能够合理扩展**，而不是越复杂越高级。
3. **不伪造数据。** 扩展性分析说"哪类瓶颈会先出现"，不编造具体 QPS 数字；没有数据就明说没有。
4. **只审不改。** 架构调整交 refactor / code-writer 分步实施；本 Skill 产出判断与方案。
5. **规模匹配。** 结合当前系统规模判断（用户量/QPS/数据量/增长速度），不假设无限大流量。
6. **好设计也要说。** 值得保留的架构设计明确写 GOOD。
7. **不越界。** 代码级设计问题归 code-reviewer，安全漏洞归 security-reviewer，性能测量归 performance；本 Skill 管系统级结构。

## 评审模式

| 模式 | 触发 | 做法 |
|---|---|---|
| 快速评审 | 单服务/单模块/单个架构疑问（如"这两个模块要不要合并"） | 只走与问题相关的 Step，报告只保留：系统概览、架构图、核心问题、最终建议 |
| 深度评审（默认对"全面审一遍/上线前/架构决策"） | 全系统、多服务、重大重构前 | 走全 Step，输出完整 11 节报告 |

## 工作流

### Step 1 理解系统

- 用 **codebase-understanding**（深度版，或复用已有项目地图）搞清：项目结构、技术栈、启动方式、服务列表、模块列表、服务依赖、数据库、Redis、MQ、第三方服务、AI 模型/Agent/Tool/RAG/MCP。
- 微服务项目画出调用图：

```text
Gateway
  ↓
Service A
  ↓
Service B
  ↓
Database

Service → Redis
Service → MQ
```

- 明确本次审查范围（整个系统 / 某几个服务 / 某类问题）。

### Step 2 系统边界

- **用户**：谁在使用系统。
- **系统**：系统负责什么。
- **外部系统**：支付、短信、邮件、LLM、第三方 API、对象存储、消息系统。
- 明确哪些属于系统内部、哪些属于系统外部。

### Step 3 模块边界

- 模块职责是否清晰、是否高内聚低耦合。
- 循环依赖、跨模块直接访问数据库、公共模块越来越大、业务代码混入基础设施模块。
- 核心问题：**一个模块到底应该负责什么？** 一个模块什么都负责 → 必须重点报告。

### Step 4 微服务边界（是微服务才做）

- 拆分是否按业务边界；是否过度拆分；是否有服务过大。
- 服务间依赖是否复杂；**是否存在循环调用**：

```text
A → B
B → C
C → A
```

- **是否存在过长同步调用链**：

```text
A
 ↓
B
 ↓
C
 ↓
D
 ↓
E
```

- 大量同步 RPC、分布式事务风险。

### Step 5 API 与服务通信

- 通信方式盘点：REST、RPC、Feign、gRPC、MQ、WebSocket、SSE。
- 判断什么时候应该同步调用、什么时候应该异步消息。
- 重点检查：超时、重试、熔断、限流、降级、幂等、服务不可用时的行为。

### Step 6 数据库架构

- 数据库职责、表设计、数据归属；服务是否跨库访问、是否存在共享数据库。
- 事务边界、数据一致性、索引、数据增长、分库分表需求。
- **不要为了"高级"而建议分库分表**——必须根据数据量、QPS、增长速度、业务场景判断是否真的需要。

### Step 7 Redis 架构

- Redis 为什么存在、缓存什么、Key 如何设计、过期策略、缓存一致性、热点 Key、大 Key、分布式锁。
- Redis 是否承担了不应该承担的业务（当数据库用、当消息队列用）。
- 核心判断：Redis 是真正解决问题，还是"为了使用 Redis 而使用 Redis"。

### Step 8 MQ 架构

- 为什么使用 MQ、哪些业务在用；Topic/Queue、Producer、Consumer。
- 消息可靠性、幂等、重试、死信、顺序、消息积压。
- 重点分析：`业务操作 → 数据库 → MQ → 消费者` 这条链是否可能出现数据不一致。

### Step 9 分布式一致性

- **数据库 + Redis**：DB 成功、Redis 失败怎么办？
- **数据库 + MQ**：DB 成功、MQ 发送失败怎么办？
- **多服务**：订单服务 → 库存服务 → 支付服务，中间某个服务失败怎么办？
- 检查：最终一致性、幂等、重试、补偿、状态机、分布式事务。
- **不要看到多个服务就强行建议分布式事务**——优先考虑幂等 + 重试 + 补偿 + 状态机。

### Step 10 可靠性

- 单点故障；服务宕机、Redis 宕机、MQ 宕机、数据库宕机、第三方 API 宕机、网络异常时系统行为。
- 超时、重试、熔断、降级、限流是否具备。
- 核心问题：**如果一个依赖挂了，整个系统会不会跟着挂？**

### Step 11 性能与扩展性

- QPS、响应时间、并发、数据量与增长、服务扩容、数据库压力、Redis 压力、MQ 吞吐、网络调用。
- 系统的主要瓶颈在哪里。
- 核心问题：**如果用户从 1 万增长到 100 万，会首先出现什么问题？**
- 结合当前系统规模判断，不假设无限大的流量。

### Step 12 可观测性

- 日志、Trace ID、Metrics、Monitoring、Tracing、Error Tracking、健康检查、慢请求、慢 SQL。
- 核心问题：**出现线上问题以后，能不能快速知道哪里出问题？**

### Step 13 AI / Agent 架构（涉及才做）

分析链路：`User → API → Agent → LLM → Tool → RAG → Database / Vector DB`。

- **Agent**：Agent Loop、状态管理、Tool 调度、最大循环次数、错误恢复、超时。
- **LLM**：Provider 抽象、Model 管理、Retry、Rate Limit、Token 管理、Streaming。
- **RAG**：数据 ingestion、Embedding、Vector DB、Retrieval、Rerank、Context、权限过滤。
- **MCP**：Tool、Resource、Server、权限、生命周期。

重点判断：**AI 部分是不是和业务代码严重耦合**（换模型/换 Provider 要不要改遍业务代码）。

### Step 14 安全架构（结合 security-reviewer）

- 检查 Authentication、Authorization 在 Gateway、Service、数据库、Redis、MQ、AI Tool、MCP 各层的分布。
- 核心判断：**安全控制应该放在哪一层**——理想是分层：Gateway 做认证、Service 做授权、数据层做数据权限；**不能只依赖 Gateway**。

### Step 15 定级与问题卡

| 级别 | 定义 |
|---|---|
| P0 | 严重架构风险：数据一致性无法保障、单点全局崩溃、边界完全混乱 |
| P1 | 高优先级：明确的可靠性/扩展性/一致性隐患 |
| P2 | 中等问题：特定条件下暴露 |
| P3 | 低优先级 |
| GOOD | 优秀设计，值得保留 |
| INFO | 值得关注但不一定需要修改 |

每个问题一张卡：

```
【等级】P0 / P1 / P2 / P3 / GOOD / INFO
【位置】模块 / 服务 / 文件
【问题】具体是什么
【原因】为什么是问题
【影响】可能造成什么后果
【场景】在什么情况下会暴露
【建议】怎么改
【优先级】是否值得现在改
```

## 最终报告

```
# Architecture Review Report

## 1. 系统概览
介绍整个系统：做什么、服务谁、什么形态、什么规模。

## 2. 当前架构图
Mermaid 或 ASCII；复杂系统给出多条关键链路（核心业务、支付/消息、AI 链路）。

## 3. 模块 / 服务边界
说明每个模块负责什么，边界是否清晰。

## 4. 数据流
请求 → 服务 → 数据库 / Redis / MQ 怎么流动。

## 5. 核心问题
按 P0 → P1 → P2 → P3 排序，每条一张问题卡。

## 6. GOOD
值得保留的架构设计。

## 7. 最值得修改的 5 个问题
按 收益 × 风险 ÷ 修改成本 排序。

## 8. 扩展性分析
业务规模增长 10 倍 / 100 倍，可能首先出现什么瓶颈。
不伪造具体 QPS 数字。

## 9. 可靠性分析
DB / Redis / MQ / Service / LLM 出现故障，会发生什么。

## 10. 可观测性
目前是否容易定位线上问题。

## 11. 最终建议
短期 / 中期 / 长期 三个阶段的架构建议。
```

## 与其他 Skill 配合

完整链路：**codebase-understanding（读）→ architecture-reviewer（架构审查）→ code-reviewer（代码设计）/ security-reviewer（安全）/ performance（性能）→ refactor / code-writer（实施架构调整）→ test-writer（验证）→ bug-finder（找回归）→ bug-fixer（修复）→ architecture-reviewer（重新审查）**。形成：理解 → 架构审查 → 代码审查 → 安全审查 → 性能分析 → 修改 → 测试 → 重新审查。

- **codebase-understanding（读）**：Step 1 的上下文来源，架构图与模块清单的底稿；已有项目地图直接复用。
- **code-reviewer（审）**：分工——reviewer 管代码级设计（分层、职责、可测性），本 Skill 管系统级（边界、通信、一致性、可靠性、扩展性）；reviewer 发现问题背后是系统性架构问题时，升级交本 Skill。
- **security-reviewer（安）**：安全架构分层（控制放哪一层）结合它的漏洞发现；它发现的越权问题常指向架构层鉴权缺失。
- **performance（能）**：它定位的瓶颈若根因在架构（调用链过长、同步 RPC 链），交本 Skill 评估；本 Skill 的优化建议实施后由它复测。
- **refactor / code-writer（改）**：确认值得改的架构调整按问题卡交它们**分步**实施——小步、可回退、每步有测试。
- **test-writer（测）/ bug-finder（查）/ bug-fixer（修）**：架构调整后验证功能、寻找回归问题、修复缺陷。

重要原则：架构审查必须基于当前项目真实代码和真实业务；不要为了让架构看起来"高级"而增加复杂度；优先选择**简单、可靠、可维护、能够满足当前需求**的方案。
