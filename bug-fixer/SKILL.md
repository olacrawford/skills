# Bug Fixer（Bug 修复 · 通用）

接手一个已确认的 Bug（来自 bug-finder 的报告卡，或用户手里的报错信息/堆栈/日志），负责把它真正修掉：定位根因 → 最小修改 → 实际验证 → 确认修复。目标不是"让这条报错消失"，而是"这类问题不再发生，且没有修出新问题"。

## 铁律（贯穿全程）

1. **修根因，不修表象。** 报错点往往只是受害者。禁止用吞异常、加特判绕过、删业务逻辑、放宽校验等方式让问题"看起来消失"。
2. **定位前不动代码。** 说不出根因之前不改一行；动手前必须能回答"为什么这里出问题、为什么改这里能根治"。
3. **最小修改。** 只改根因相关的代码；不顺手重构，不改无关代码，不删业务逻辑规避问题。
4. **不为通过测试而作弊。** 禁止改测试断言、删失败用例、静默吞掉异常来"变绿"。测试失败 → 分析原因 → 继续修，而不是汇报一句"测试失败"了事。
5. **没验证就不算修复。** 能跑的编译/测试/复现都实际跑；没实际运行的只能写"理论上正确"，禁止写"已验证"。
6. **修完必须回归。** 修复不能引入新 Bug：原功能、API 行为、并发、事务、缓存、MQ 逐项确认（Step 7）。
7. **无法确认不强修。** 缺环境、缺日志、无法复现、报告有误 → 停下，输出【当前无法确认】，不强行修改。

## 工作流

### Step 1 理解 Bug（先定位，不动代码）

输入分两类：

**A. 用户给了 bug-finder 的报告卡** → 逐字段读：

- 【问题位置】【问题】→ 打开对应代码核对。报告是线索不是结论，发现判断有误（位置不对/根因不对）以实际代码为准，并在最终报告说明。
- 【触发条件】【执行过程】→ 得到复现路径。
- 【影响】→ 明确修复的验收标准。
- 【修复建议】→ 方案起点，不是照抄：先自己验证根因成立。
- 【验证方法】→ 直接进 Step 6 的验证计划。

**B. 用户只有报错/堆栈/日志/代码片段/现象描述** → 自行定位：

- Stack Trace：从第一个**项目自己的帧**开始（跳过框架帧），打开文件到行号；再看 Caused by 链。
- 日志：按报错关键字 / TraceId / 请求参数 grep 源码定位。
- 现象描述：先确定入口（哪个接口/MQ 消费者/定时任务），再沿调用链往下。

无论哪种输入，动手前补齐四件事：**现象、触发条件、涉及的代码位置、出错的值/状态**。

### Step 2 定位根因

沿调用链回答七个问题：

1. Bug 从哪里开始？（源头，不一定是报错点）
2. 哪个方法出现异常？
3. 为什么会出现异常？
4. 数据是如何流动的？从入口到出错点每一步的值是什么？
5. 哪个状态出错了？（DB 记录 / 缓存 / 内存变量 / Agent 上下文）
6. 有没有并发、事务、缓存、MQ 参与或放大？
7. 为什么现有代码没有阻止它？（缺校验？缺锁？缺重试？边界漏了？）

根因判定标准：**改了这里，这个问题在所有同类场景下都不会再发生**。只改报错点、换个参数还会炸的，不是根因。

报告中区分三层，说清链条：表面现象（如 NPE）→ 直接原因（如 user 为 null）→ 根因（如上游创建订单时没关联用户）。

### Step 3 制定修复方案

动手前先给用户一份简报：

```
【根因】一句话说清真正原因
【修复方案】怎么改、为什么改这里能根治
【修改范围】要动的文件/类/方法
【风险】可能影响什么（调用方/数据/并发/API 行为）
```

按复杂度决定是否等确认：

- 简单问题（明显笔误、缺判空，根因一目了然）→ 简报后直接改，不等确认。
- 一般问题 → 简报后直接实施，用户可随时打断。
- 需要跨模块改动 / 公共 API 契约变更 / DB 结构变更 / 大范围重构 → 简报后停下等用户确认；若认为只有重构才能根治，必须说明为什么最小修改解决不了。

### Step 4 实施修改

- **最小修改**：diff 越小越好，每处改动都能对应到根因。
- **风格跟随**：读相邻代码，沿用项目的分层、命名、异常体系、日志方式。
- **复用优先**：用项目现有的工具类/异常/重试/锁实现，不随意引入新依赖。
- **兼容优先**：保持 API 兼容、数据库结构兼容，除非 Bug 本身就是契约错误且用户已确认要改。
- **不删业务逻辑规避问题**；不改断言让测试通过（除非断言本身写错了，需说明理由）。

### Step 5 修复后重点检查

对修复本身逐项检查：修复在这些场景下是否正确、这些场景是否被修复破坏。

业务逻辑：正常流程 / 异常流程 / 边界条件（空、0、负数、极大、超长）/ 重复请求 / 重复执行（幂等）。

按项目实际用到的技术域：

| 域 | 检查项 |
|---|---|
| Java / Go | 空指针、类型转换、并发安全、线程池 / Goroutine 泄漏、Channel、锁（范围与死锁）、生命周期 |
| 数据库 | SQL 正确性、事务边界、并发更新、数据一致性、索引（修复是否引入慢查询） |
| Redis | Key、TTL、缓存一致性、分布式锁、原子操作 |
| MQ | 重复消费、消息丢失、ACK、重试、幂等（修复后重试路径还幂等吗） |
| AI / Agent | Token 限制、无限循环、Tool 调用失败处理、Prompt Injection、API 超时与重试、上下文、Agent 状态 |

### Step 6 实际验证

按顺序尽量执行，结果原样记录：

1. 编译 / 构建。
2. 静态检查 / 类型检查。
3. 覆盖改动点的既有单元测试。
4. 集成测试（如有）。
5. **复现验证：用原始触发条件重新跑一遍，确认不再复现** ← 这是"确认修复"的核心；测试通过 ≠ Bug 消失。
6. 相关 API 测试（能起服务就打真实请求）。
7. 必要的手动验证。

测试失败的处理：分析原因 → 是我改坏的，继续修；暴露出另一个 Bug 的，如实报告；断言本身错的，说明理由并经确认才改。

环境缺 DB / 第三方服务 / 真实数据而无法验证的，列入【未验证清单】，明确标注"理论上正确"。

### Step 7 回归检查（防修复引入新 Bug）

- 原 Bug 真的消失（原触发条件复验）。
- 原有功能还正常（改动点的调用方、既有测试）。
- 没引入新异常（编译警告、日志、新测试）。
- API 行为没变（入参/出参/状态码/错误语义）。
- DB 操作没被破坏（事务/SQL）。
- 并发安全、事务边界、缓存一致性、MQ 消息处理没被影响。

### Step 8 最终输出：Bug 修复报告

```
# Bug 修复报告

## 1. Bug
原来的问题：现象 + 触发条件（2~3 句）。

## 2. 根因
为什么产生 Bug，说清"表面现象 → 直接原因 → 根因"链条。

## 3. 修复
- 文件：<path>
- 类/方法：<Class#method>
- 核心修改：改了什么，为什么这样改能根治。

## 4. 验证
实际执行的：编译 / 测试 / 复现验证 / API 测试 / 其他，逐项给命令与关键结果。
区分标注【实际验证通过】/【理论正确，未实际验证】；无法验证的列入未验证清单。

## 5. 影响范围
可能影响的功能/调用方/数据；发现但未处理的既有问题（带 `路径:行号`）。

## 6. 最终结论
- Bug 是否确认修复（基于复现验证结果）
- 是否还有未解决的问题
- 是否存在需要进一步观察的风险
```

硬性规则：没有实际运行过测试/复现，第 4、6 节只能写"理论上正确"，不允许出现"已验证"。

## 特殊情况：不强修

遇到以下情况，停下，不强行修改：

- Bug 报告本身有误，或当前代码实际没有这个 Bug → 以代码证据为准说明。
- 无法复现（缺触发条件、缺环境）。
- 缺必要条件：日志、数据库数据、第三方服务、配置。

输出：

```
【当前无法确认】
- 已确认的部分：（查到了什么，证据坐标）
- 无法确认的部分及原因：
- 需要用户提供：（具体到可执行，如"XX 服务 XX 时间段的日志 / XX 表的样本数据 / 复现步骤"）
```

## 与其他 Skill 配合

标准链路：**codebase-understanding（读）→ bug-finder（查）→ bug-fixer（定位根因 → 修改 → 验证）→ test-writer（回归测试）→ code-reviewer（审，最终质量把关）**。

- **bug-finder（上游）**：报告卡是本 Skill 的首选输入（用法见 Step 1-A）。用户贴整份检测报告时，按 P0→P3 逐个修复，每个 Bug 出一份修复报告。
- **codebase-understanding（读）**：Bug 涉及陌生模块时，先调用其焦点模式拿调用链与依赖清单，不盲目全文搜索；之前生成过项目地图就直接复用其中的坐标。
- **code-writer（写）**：分工——Bug 修复走本 Skill，新功能/常规改动走 code-writer，纯结构重构走 refactor。本 Skill 的修改纪律（风格跟随/复用优先/最小改动面）与 code-writer 一致；修复中发现需要补一个完整新功能（如引入校验框架）超出修复范围时，记录到报告，交给 code-writer。
