# AI / Agent / RAG 专项陷阱清单

AI 项目的特殊性：输入不可枚举、输出不确定、调用有真金白银成本。检查重心：**输入边界、循环终止、上下文管理、成本、安全**。

## 安全（最高优先级）

- **Prompt 注入**：用户输入直接拼进 prompt（尤其拼进 system/指令区）；检索来的外部内容（网页、用户上传文档）未做隔离直接进上下文——间接注入。识别特征：字符串拼接 / 模板填充处。找到具体拼接点才报；只有风险面没有证据 → 未确认。
- **工具执行安全**：LLM 生成的参数不校验直接执行——SQL 工具（注入/全表删）、文件工具（路径穿越）、shell 工具（命令注入）。工具参数 schema 有没有服务端校验是关键。
- **敏感数据泄露**：用户隐私/密钥/内部数据进 prompt 或日志；LLM 输出未经滤直接渲染到前端（markdown/HTML 注入）。

## Agent 行为

- **无限循环**：agent 主循环无 max_iterations / 无终止条件；工具失败后原样重试（相同输入必然相同失败）。识别：找主循环，看退出条件是否完备。
- **工具调用失控**：LLM 幻觉调用不存在的 tool → 报错循环；一个工具的输出触发对另一个工具的循环调用。
- **Tool 参数问题**：schema 定义与实际 handler 期望不一致；必填参数缺省时 handler 崩溃；枚举外值未校验。
- **Agent 状态**：会话状态存进程内存 → 重启丢失、多副本不一致；用户上下文放单例/共享变量 → 并发会话串状态（对照 java-spring-pitfalls 的 ThreadLocal 串数据，P0）。

## 上下文与 Token

- 长对话无裁剪/摘要机制 → 超上下文限制报错或成本线性膨胀。
- 检索内容全量塞进 prompt，无长度预算。
- 历史消息无截断但模型上下文有限 → 老会话必然崩。

## RAG 链路

- **检索为空无处理**：query 无命中时把空上下文给 LLM → 幻觉输出。识别：retriever 结果直接拼 prompt，无空判断分支。
- **数据过期/删除不同步**：源数据已删/已改，向量索引还在 → 检索出已删除内容（合规风险）；有无重建/同步机制。
- **Embedding 一致性**：换 embedding 模型后旧向量未重建 → 维度不匹配报错或语义漂移；查询与入库用了不同模型（识别：两处模型名字符串是否一致，配置化则核对配置）。
- chunk 策略切坏语义（按固定长度硬切、无重叠）→ 检索命中但内容残缺，回答质量差（P2~P3，业务容忍度定级）。
- 元数据过滤条件写错 → 该过滤的没过滤（越权检索他人文档，可能是 P0）。

## LLM API 调用

- 未设超时；超时/失败无重试，或重试无退避无上限（429 时继续打 → 雪上加霜 + 烧钱）。
- 流式响应中途断开的处理（半截输出直接给用户？）。
- 无 fallback/降级模型；主模型挂了服务全挂。

## 成本

- 无 token 计量与预算上限；单请求无 max_tokens 约束。
- 循环/递归里调 LLM 的成本放大（每次循环全量重发历史）。
- 相同请求无缓存 → 重复计费。

## 输出提醒

AI 项目定级时把"触发概率"和业务场景绑定：内部工具的低质量回答可能是 P3，面向 C 端的幻觉回答可能是 P1。拿不准 → 未确认并说明需要的信息（线上 query 分布、检索命中率等）。
