# 数据库 / Redis 专项陷阱清单

## 数据库

**SQL 正确性**
- UPDATE/DELETE 漏 WHERE 或条件恒真（拼 SQL 时 `1=1` 后没接上业务条件）→ 全表改写，P0。
- 逻辑删除不彻底：查询漏带 `del_flag` 条件；软删数据与唯一索引冲突（删了就永远插不回）。
- join 条件写错（on 条件放 where 导致语义变化）、隐式类型转换（字符串列传数字使索引失效）。

**性能**
- 索引失效：联合索引不满足最左前缀；索引列上用函数/运算；`like '%xx'` 前缀通配；or 两侧有非索引列。
- N+1：for 循环内单条查询；ORM 懒加载在循环中触发。识别特征：`for (... ) { mapper.selectById(...) }`。
- 深分页：大 offset 全量扫描；游标/延迟关联缺失。P2~P3 视数据量。
- 大表无分页 count(*)。

**事务与一致性**
- 并发更新丢失：读-改-写三步无版本号（乐观锁）/无 `select for update`/无条件更新。
- 超卖/扣负：扣减 SQL 无 `AND num >= ?` 防御；余额/库存类字段重点查。
- 唯一性只靠应用层先查后插，无 DB 唯一索引 → 并发插入重复数据。
- 跨库/跨表多步写，无事务或事务内夹远程调用。
- 迁移脚本与实体定义不同步（新字段没迁移 / 实体没更新）。

**其他**
- 排序字段不唯一导致翻页重复或丢数据（应补主键做次序）。
- 金额/精度用 float/double 存储。

## Redis

**三大经典模式（先确认项目是否有对应场景再判级）**
- 缓存穿透：查询不存在的数据，无空值缓存/布隆过滤器 → 恶意请求直达 DB。
- 缓存击穿：热 key 过期瞬间大量并发重建，无互斥锁/逻辑过期 → DB 瞬时打爆。
- 缓存雪崩：大量 key 同一时刻过期（TTL 未加随机）；Redis 不可用时无降级/隔离 → 请求压垮 DB。

**缓存一致性**
- 识别项目用的模式（先删缓存后更新 DB / 先更新 DB 后删缓存 / 延迟双删 / 订阅 binlog），评估不一致窗口：
  - 先删后更：删除到更新完成之间，读请求把旧值写回缓存 → 长期脏数据，P1。
  - 先更后删：更新到删除之间的短暂旧读，P2~P3。
  - 注意：不要把理论窗口直接当 P0/P1——结合业务容忍度定级，说不清就 P2 或未确认。

**Key / TTL**
- 集合类 key（list/set/zset/hash）只增不减且无过期 → 内存无限增长。
- 大 key（大 value、百万成员）；热点 key 无本地缓存防护。
- TTL 忘设；应随机的 TTL 写成固定值。

**分布式锁（高危区）**
- setnx 后无过期时间 → 持锁方宕机死锁，P1。
- 锁 value 不唯一（固定值）→ 释放时误删他人的锁，P1。正确姿势：value=唯一标识 + Lua 原子释放。
- 锁过期时间 < 业务耗时且无续期 → 锁提前失效并发进入。
- 拿到锁后仍 check-then-act（锁没覆盖完整临界区）。
- get+set 分开的非原子操作（应 INCR/DECR/Lua/事务）。
- 序列化不一致：写入与读取用不同 serializer → 读不到/反序列化失败。
- Redis 挂掉/超时的降级路径是否存在（直连 DB 的兜底会放大故障还是隔离了故障）。
