# Bug Finder（Bug 检测 · 通用）

从「代码实际运行可能出问题」的角度找 Bug：业务逻辑、并发、数据一致性、异常流程。只发现问题、分析问题、提出修复方案；**默认不修改任何代码**。

## 铁律

1. **只读不改。** 不修改任何业务代码。产出是报告 + 修复建议，修不修由用户决定，修复执行交给 bug-fixer。
2. **运行时视角。** 只关心跑起来会不会出错。命名、注释、格式等风格问题不是 Bug，不报告（最多在报告附注一句带过）。
3. **证据优先，防误报。** 报告一个 Bug 必须满足至少一条：逻辑可证明有问题 / 能构造明确触发条件 / 基于项目实际架构可判断的风险。纯"理论上可能"→ 进「未确认问题」，不得写成 Bug。
4. **数量不重要。** 不为凑数硬找。没发现高危问题就如实说"未发现 P0/P1"——这是有价值的结论，不是失职。
5. **沿调用链分析。** Bug 藏在接缝处：入口校验、事务边界、锁、缓存读写、MQ 收发、下游调用。孤立看单个文件得出的结论可信度低，必须结合上下游。
6. **影响写实际后果。** 写"库存扣成负数，需人工补偿订单"，不写"可能导致一些问题"。

## 工作流

### Step 1 划定范围并理解项目

- 检查对象可以是：整个项目 / 单个模块 / 一段代码。小片段直接进 Step 2，跳过项目理解。
- 指定了模块 → 焦点检查；未指定 → 默认检查**核心业务链路**（交易、支付、库存、鉴权这类出错代价最高的路径）。
- 相关模块陌生 → 调用 **codebase-understanding**（焦点模式），拿到：模块职责、关键调用链、外部依赖（DB/Redis/MQ/第三方）。
- 明确记录本次检查范围（哪些模块/链路），以及**明确没检查什么**——写进报告第 4 节。

### Step 2 沿调用链做逻辑分析

对每条关键调用链，逐项过通用清单：

| 维度 | 要问的问题 |
|---|---|
| 正常流程 | happy path 完整吗？每个分支都有明确行为（有漏 return / 漏持久化吗） |
| 异常流程 | 每个失败点（网络/DB/下游）失败后：回滚？重试？静默吞掉？用户看到什么 |
| 边界与空值 | 空集合、null、0/负数、超长输入、极大分页 |
| 参数异常 | 入口参数校验了吗？负数金额、超范围页码、非法枚举能进来吗 |
| 状态转换 | 状态机允许非法跳转吗（已取消的还能发货？已支付的能重复退款？） |
| 重复调用 | 同一操作执行两次会怎样（幂等性） |
| 并发执行 | 两个请求同时跑这段代码会怎样——重点找 **check-then-act** 模式（先查后改无保护） |
| 超时 | 下游慢了/挂了会怎样，调用有没有设超时 |
| 重试 | 失败重试吗？非幂等操作 + 重试 = 放大问题 |
| 数据一致性 | 跨存储写（DB+Redis、DB+MQ、双库）成功一半怎么办 |

### Step 3 按技术域专项检查

以 manifest/配置为证据，只检查项目**实际用到**的技术域，读对应参考文件逐条核对：

- Java/Spring → `references/java-spring-pitfalls.md`
- 数据库 / Redis → `references/storage-pitfalls.md`
- MQ / 微服务 → `references/mq-and-microservices.md`
- AI / Agent / RAG → `references/ai-rag-pitfalls.md`

### Step 4 定级

| 级别 | 定义 | 典型例子 |
|---|---|---|
| P0 | 系统不可用、数据损坏、严重安全漏洞 | 超卖/余额扣负、越权访问他人数据、SQL 注入、ThreadLocal 串用户、死锁打挂服务 |
| P1 | 线上大概率产生错误 | 事务失效导致数据不一致、重复消费导致重复下单、常见路径 NPE、消息丢失 |
| P2 | 特定条件下出现 | 边界值、罕见并发时序、深分页、缓存一致性窗口 |
| P3 | 低风险或健壮性改进 | 缺重试退避、失败日志缺失影响排查 |

定级方法：触发概率 × 影响后果。**说不出触发条件的问题不能定级**——放「未确认」。

### Step 5 写 Bug 报告卡

每个 Bug 一张卡（模板与示例见下），字段顺序固定。

### Step 6 输出报告

按下方「最终输出格式」组装，Bug 按 P0→P3 排序；发现严重问题时在最前面用一行醒目提示。

## Bug 报告卡

```
【严重程度】P0/P1/P2/P3
【问题位置】文件路径 + 类名/函数名 + 方法名，尽量到行号
【问题】哪里有问题（一句话说清缺陷本身）
【触发条件】什么情况下会出现
【执行过程】用实际调用顺序解释怎么发生的
【影响】会造成什么实际后果
【修复建议】应该怎么改（方案级别即可，不写代码）
【验证方法】修完后怎么确认修好了
```

示例（校准用）：

```
【严重程度】P1
【问题位置】service/OrderService.java # createOrder()，第 88-96 行
【问题】先查库存再扣减，两步之间无锁、无条件更新（check-then-act）
【触发条件】两个请求同时购买同一 SKU，且剩余库存为 1
【执行过程】请求 A 读到库存=1 → 请求 B 也读到库存=1 → A 扣减成功 → B 也扣减成功 → 卖出 2 件，库存变为 -1
【影响】超卖；库存负数；需人工补偿订单
【修复建议】扣减改为条件更新（UPDATE ... SET num=num-1 WHERE sku=? AND num>=1），受影响行数为 0 时返回库存不足；或对该 SKU 加分布式锁
【验证方法】并发压测：库存=1 时两线程同时下单，断言恰好 1 单成功、库存为 0
```

## 最终输出格式

```
# Bug 检测报告

## 1. 项目整体风险
当前整体情况 3~5 句：检查了什么、整体健康度、最担心的方向。

## 2. Bug 列表
按 P0 → P1 → P2 → P3 分组，每组内按影响排序；每条一张报告卡。

## 3. 最值得优先修复的问题（最多 5 个）
每条：为什么优先修 / 不修会有什么后果 / 修复难度（低中高 + 理由）。

## 4. 检查范围
实际检查了哪些模块、文件、调用链；**明确列出没检查的部分及原因**。

## 5. 未确认问题
证据不足但值得警惕的点 + 需要什么信息才能确认（配置值、运行数据、并发量级等）。
```

## 与其他 Skill 配合

- **codebase-understanding（读）**：Step 1 的理解来源，提供调用链与依赖清单；已有项目地图则直接复用坐标。
- **bug-fixer（修）**：本 Skill 只产报告。用户决定修复后，把对应 Bug 卡交给 bug-fixer 执行——【问题位置】【触发条件】用于定位与复现，【修复建议】成为方案起点（bug-fixer 会自行验证根因，不照抄），【验证方法】成为验证计划；整份报告交付时按 P0→P3 逐个修复，每个 Bug 出一份修复报告。
- **code-reviewer（审）**：系统性的质量评审（设计/性能/安全/测试/工程规范等全维度）由 code-reviewer 负责，本 Skill 专注"找运行时 Bug"；评审中发现的新明确 Bug 交回 bug-fixer 修复。
- 闭环：**读（codebase-understanding）→ 查（bug-finder）→ 修（bug-fixer）→ 审（code-reviewer）**；安全专项交 security-reviewer。
