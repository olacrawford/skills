# Code Writer（代码编写 · 通用）

在**现有项目**里写代码：新功能、修 bug、重构、加接口。产出标准：代码像这个项目里的人写的，通过实际验证，如实汇报。

## 铁律（贯穿全程）

1. **不理解不下笔。** 动手前必须读过相关代码：目标文件、它的调用方、以及一个相似功能的已有实现。不猜测项目结构。
2. **按项目的方式写。** 先看相邻代码的风格（分层、命名、错误处理、DI、日志），新代码沿用同一套；不为省事破坏现有架构。
3. **最小改动面。** 不改无关代码，不顺手重构，不无意义引入新依赖，不重复实现已有功能。复用优先。
4. **计划先行。** 中大型任务动手前先把实现方案告诉用户；只有微型任务可直接执行（见"规模分级"）。
5. **能验证就验证。** 能跑的编译/静态检查/测试都要实际运行，原样报告结果；没验证的部分明确说"未验证"，禁止只说"理论上没问题"。
6. **不隐藏错误。** 编译失败、测试挂了、发现既有 bug，都如实写进汇报；不为了"看起来完成"而掩盖或静默绕过。
7. **不确定要说明。** 需求歧义、方案取舍、推断的默认值——明确列出，不许默默替用户做重大决定。

## 规模分级（决定流程繁简，防机械走流程）

| 级别 | 判断标准 | 流程 |
|---|---|---|
| S 微型 | 单文件小改：文案、常量、配置值、明显小 bug | 跳过方案，直接改 → 自检 → 精简汇报 |
| M 标准 | 单模块内完整改动：新接口、新字段、一条完整方法链 | 完整流程：当轮给出方案后**直接实施**，用户可随时打断 |
| L 复杂 | 跨模块、新表/迁移、新依赖、公共 API 契约变更、架构级调整 | 完整流程，方案给出后**停下等用户确认**再动手 |
| 破坏性 | 删数据/删文件、改公共契约、大规模重构 | 任何规模都必须先确认 |

## 工作流

### Step 1 理解需求

1. 用一句话复述需求：**输入 → 处理 → 输出**。
2. 列出隐含业务规则与边界：空值、重复提交、并发、权限、数量上限、失败回滚。
3. 有明显歧义 → 先指出问题再继续；小歧义 → 选最合理默认值并在方案中标注。
4. 明确写"本需求不包含 X"，防止范围蔓延。

### Step 2 阅读现有代码

按顺序做三件事：

1. **理解相关模块**：
   - 项目之前分析过 → 直接用已有项目地图的坐标；
   - 相关模块复杂或陌生 → 调用 **codebase-understanding** skill（焦点模式，只看相关模块），不要全量重跑；
   - 微型改动 → 至少读：目标文件 + 调用方 + 一个相似实现。
2. **找相似实现**：Grep 定位项目里最接近的已有功能（同层级、同类型的方法/接口），它就是新代码的模板。
3. **提取项目风格**：按 `references/project-conventions.md` 的清单，读目标层级 2~3 个现有文件归纳出"这个项目怎么写代码"。

### Step 3 制定实现方案（对用户可见）

```
## 实现方案
- 需求复述：输入 → 处理 → 输出
- 改动清单：
  - 修改 `path/to/file`：改什么、为什么
  - 新增 `path/to/file`：职责、为什么放这个位置
- 复用说明：复用了项目哪些现有能力（类/工具/模式），避免重复造轮子
- 影响面：影响哪些调用方/模块；是否需要 DB 迁移、配置变更、API 契约变更、文档更新
- 取舍与默认值：不确定的点 + 我选的默认值及理由
```

按规模分级决定：M 级呈现后继续执行，L 级呈现后等确认。

### Step 4 编写代码

- **复用优先**：写之前先搜项目里有没有现成的工具类/公共方法/基类（utils、common、base 目录）；有就用，没有才写新的。
- **风格跟随**：命名、缩进、注释密度与语言（中/英）、错误处理方式、DI 风格、返回值包装，全部与相邻代码一致（细则见 `references/project-conventions.md`）。
- **架构服从**：新逻辑放进项目已有的分层位置（该在 service 的不写进 controller，该在 dao 的 SQL 不上浮）；沿用项目统一的异常体系与响应包装。
- **依赖克制**：不引入新依赖除非确有必要；确需引入在方案中说明理由与版本，L 级变更走确认。
- **无关不动**：顺手发现的无关问题（bug、坏味道）记录到汇报的【风险】，不顺手修、不评论式重写。

### Step 5 完成后自检

逐项过 `references/self-check.md` 的清单：编译/类型/导入、空指针、参数校验、异常处理、边界条件、并发、数据库、Redis/MQ、API 兼容性、回归影响。各语言可执行的检查命令在参考文件里，**能跑的实际跑**。发现问题当场修。

### Step 6 测试

按 `references/testing.md` 执行：

- 项目有测试：**先跑与改动相关的既有测试**确认没改坏；按项目已有测试风格补新测试（先读同类测试再写，模仿其 mock/fixture 方式）；改动面大时跑全量。
- 项目没有测试：至少做可执行验证——编译、静态检查、类型检查、启动冒烟（若可），并在汇报里明确列出**未验证清单**。
- 测试挂了先判断：是我改坏的（修），还是改动前就挂的（记录进【风险】，不擅自大修）。不为了通过测试而改断言，除非需求本身就是行为变更且在汇报中说明。

### Step 7 最终汇报（固定格式）

```
【需求】
实现了什么（1~3 句）

【修改文件】
- 修改：<path>（一句话改了什么）
- 新增：<path>（一句话职责）

【实现方式】
核心实现逻辑：关键类/方法名、复用了什么、走了哪条调用链

【测试】
执行了什么命令、结果如何（关键输出原样给出；失败如实展示）
未验证的部分明确列出

【风险】
潜在影响、已知局限、发现但未处理的既有问题（带 `路径:行号`）、建议的后续动作
```

## 与 codebase-understanding 的配合

- 分工：**codebase-understanding 管"读"（理解项目），code-writer 管"写"**。写代码前必须先"读"（Step 2）。
- 接力方式：如果用户先做过项目分析，直接引用其项目地图中的坐标（核心模块、调用链、值得重点阅读的代码），从那里定位插入点，不重复分析。
- 触发判断：需求里"理解/分析"成分大 → 先跑 codebase-understanding；"写/改"成分明确 → code-writer 内嵌调用 codebase-understanding 的焦点模式即可。

## 与 bug-fixer 的分工

- 分工：Bug 修复（有报错/异常/Bug 报告，要定位根因并修掉）走 **bug-fixer**；系统性重构（行为不变的纯结构优化）走 **refactor**；本 Skill 管新功能与常规改动。
- 边界：本 Skill 写代码过程中自己改坏的东西当场修（Step 6），不必转 bug-fixer；用户明确说"修 bug/排查根因"时，转 bug-fixer。
- 接力：bug-fixer 修复中发现还需要补一个完整新功能（如引入校验框架），超出修复范围的部分交回本 Skill。
- 收尾：较大改动完成后，用户要求 review / 质量把关时，交 **code-reviewer** 做最终评审；评审提出的重构需求交 **refactor**、补测试需求交 **test-writer**，常规小改动仍回本 Skill 执行。
- 测试：本 Skill 的 Step 6 只保证改动可验证（跑通相关既有测试、补最小新测试）；系统性的测试设计（场景矩阵、并发、一致性、集成/E2E）交 **test-writer**。
- 性能：用户报性能问题、要求压测或性能优化时走 **performance**（先测量再优化）；方案确认后，具体代码修改由本 Skill 按其方案实施。
