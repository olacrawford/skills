# Performance（性能分析与优化 · 通用）

性能优化不是"把代码写得更快"：发现性能问题 → 定位瓶颈 → 分析原因 → 建立基线 → 制定方案 → 实施优化 → 实际测试 → 对比前后。没有证据证明存在性能问题，就不要为了优化而优化。

## 铁律（贯穿全程）

1. **先测量，再优化。** 禁止看到代码就说"这里性能不好/该用 Redis/该加线程池/该异步/该加缓存"。必须尽可能回答四个问题：**慢在哪里？为什么慢？慢了多少？优化之后提升了多少？**
2. **没有数据就标"理论"。** 缺真实运行数据的问题一律标注"理论性能风险，尚未实际验证"，不冒充结论；预期收益没有实测依据就写"预期收益仅为理论判断"。
3. **不伪造数据。** 监控缺失就如实列出缺失指标；禁止编造基线、禁止伪造性能提升数字。
4. **用证据说话。** 报一个性能问题必须同时给出数据（压测/监控/EXPLAIN/Profile）或明确的代码级触发路径（循环内查库、N+1）；光"理论上慢"不算问题。
5. **不为优化而优化。** 按 收益 × 严重程度 ÷ 修改成本 排序；不为几毫秒的理论优化大规模修改系统；收益低直接说"不建议优化"。
6. **行为不变 + 小步修改。** 优化不改变业务行为；单次尽量只改一个主要因素，改完即测；不为性能牺牲明显的可维护性，不为理论性能引入复杂架构。
7. **不顺手修别的。** Bug 交 bug-fixer，结构问题交 refactor；本 Skill 只对性能负责。

## 工作流

### Step 1 理解系统

- 用 **codebase-understanding**（焦点模式，或复用已有项目地图）理解：架构、核心业务流程、关键 API、调用链、外部依赖（数据库 / Redis / MQ / 外部 API / 文件 IO / AI API）。
- 明确本次分析对象：整个系统 / 某个接口 / 某条链路。

### Step 2 建立性能基线

| 类别 | 指标 |
|---|---|
| 接口 | Avg、P50/P90/P95/P99、QPS/TPS、错误率 |
| 资源 | CPU、内存、GC（频率/停顿）、连接池使用率 |
| 中间件 | 数据库响应时间、Redis 响应时间、MQ 消费速度与堆积量、网络耗时 |
| AI | LLM API 延迟、Token 使用量、Tool/检索调用次数 |

数据来源按优先级：项目现有监控/APM > 日志里的耗时打点 > 现场压测 > 本地 Benchmark。

没有监控 → **明确列出缺失指标**，请用户补数据或授权压测；不伪造数据。

### Step 3 按域排查（只查项目实际用到的域，每个域先问"有没有证据"）

- **CPU**：高复杂度算法、无意义循环、重复计算、大量对象创建、序列化/反序列化、JSON 处理、CPU 密集型任务。
- **内存**：内存泄漏、大对象、集合/缓存无限增长、对象生命周期不合理、ThreadLocal 泄漏、大量临时对象。
- **GC（Java）**：GC 频率、停顿、堆大小、对象分配速率、Old Gen 增长、内存压力。**没有 GC 数据不随意改 JVM 参数。**
- **数据库**：
  - SQL：全表扫描、慢查询、不合理 JOIN、N+1 查询、SELECT *、大结果集、深分页、不合理排序、子查询、函数导致索引失效。
  - 索引：是否建立了合适索引、联合索引顺序、最左匹配、覆盖索引、索引失效、索引数量是否过多。
  - 事务：事务范围过大、长事务、锁等待、并发更新、死锁风险。
- **Redis**：Key 设计、Value 大小、大 Key、热 Key、Pipeline/批量操作、TTL、缓存命中率、穿透、击穿、雪崩、不合理缓存、网络往返次数。**必须先判断数据库是否真的成为瓶颈，不无脑加 Redis。**
- **MQ**：Producer/Consumer 吞吐、消费线程数、消费速度、消息堆积、重试、批量消费、ACK、消息大小、并发消费。有堆积先区分：**生产速度 > 消费速度，还是消费者本身处理过慢。**
- **Java 并发**：synchronized / Lock / CAS / Atomic / ConcurrentHashMap、ThreadPool、CompletableFuture、虚拟线程、阻塞 IO、锁竞争、线程上下文切换。两条典型恶化链：锁粒度过大 → 线程竞争 → 吞吐下降；线程池过大 → 上下文切换增加 → 性能反而下降。**线程越多不等于越快。**
- **微服务**：一次请求 Gateway → Service A → Service B → Service C → Database 的完整链路；调用链过长、同步调用过多、重复 RPC、N+1 RPC、Feign 调用过多、超时、重试、网络开销、服务雪崩。核心问题：**一次用户请求到底产生了多少次网络调用？**
- **AI / Agent**：Prompt/Context 长度、Token 使用量、LLM API 延迟、Tool 调用次数、Agent Loop 次数、RAG 检索次数、Embedding 调用次数、重复 Embedding、模型选择、Streaming、并发请求、API Retry。核心问题：**一次用户请求到底进行了多少次模型调用（LLM → Tool → LLM → Tool → LLM）？** 同时分析延迟、Token 成本、稳定性。

### Step 4 输出优化建议（每个建议一张卡）

```
【问题】哪里存在性能问题
【证据】什么数据/代码证明存在（压测/监控/EXPLAIN/Profile/代码路径）；
       缺实测的必须标"理论性能风险，尚未实际验证"
【原因】为什么导致性能下降
【方案】准备怎么优化
【预期收益】理论上改善什么；没有实测依据必须写"预期收益仅为理论判断"
【验证】优化后如何测试（用什么工具、看什么指标）
```

### Step 5 定优先级

排序公式：**收益 × 问题严重程度 ÷ 修改成本**。

| 级别 | 定义 |
|---|---|
| P0 | 立即优化：瓶颈明确 + 收益高 + 风险可控 |
| P1 | 高优先级 |
| P2 | 一般优化 |
| P3 | 低收益优化，可不做 |

不为几毫秒的理论优化去大规模修改系统。

### Step 6 实施优化（经用户确认后）

- 小步修改，单次尽量只改一个主要因素，改完即测。
- 不改变业务行为；不随意增加复杂度；不为性能牺牲明显的可维护性；不为理论性能引入复杂架构。
- 具体编码遵循 code-writer 的纪律（风格跟随、复用优先、最小改动面）。

### Step 7 性能测试与前后对比

工具按项目实际选择，不要求全装：JMeter / k6 / wrk / ab / Go benchmark / Java JMH / 数据库 EXPLAIN / Profiling / JVM 工具 / 项目现有监控。

实际执行了性能测试 → 必须输出前后对比表：

| 指标 | 优化前 | 优化后 | 变化 |
|---|--:|--:|-:|
| Avg |  |  |  |
| P95 |  |  |  |
| P99 |  |  |  |
| QPS |  |  |  |
| CPU |  |  |  |
| Memory |  |  |  |

没有实际数据的字段留空并说明原因；**禁止伪造性能提升数字。**

### Step 8 输出 Performance Report

```
# Performance Report

## 1. 性能概况
当前系统主要性能特征（基于实测/监控；缺数据的明确说明）。

## 2. 性能瓶颈
按严重程度排序，每条带证据。

## 3. 根因分析
每个瓶颈为什么产生。

## 4. 优化方案
修改什么 / 为什么 / 怎么修改（每条一张建议卡）。

## 5. 优先级
最值得做的 5 项优化（按 收益×严重程度÷修改成本 排序）。

## 6. 测试结果
优化前后实际数据对比表；没有数据就明确说明。

## 7. 剩余风险
还有哪些性能问题没有验证（理论风险清单）。

## 8. 下一步
下一步最值得做什么。
```

## 与其他 Skill 配合

完整链路：**codebase-understanding（读）→ performance（发现瓶颈）→ code-reviewer（确认设计问题）→ refactor（结构优化）/ code-writer（实施优化）→ test-writer（验证功能）→ performance（重新压测、前后对比）**。

- **codebase-understanding（读）**：Step 1 的上下文来源；已有项目地图直接复用坐标。
- **code-reviewer（审）**：分工——reviewer 在评审中只报"有明确代码证据"的单点性能问题；系统性的测量、定位与优化交本 Skill。
- **refactor（重构）**：性能瓶颈的根因是结构问题（重复计算、数据访问重复、职责混乱）时，交它做结构优化。
- **architecture-reviewer（架）**：瓶颈根因在架构层（调用链过长、服务边界不合理、单点依赖）时，交它做架构评估。
- **code-writer（写）**：具体优化代码的实施者；需要改业务行为才能解决的"性能问题"其实是需求变更，交它。
- **test-writer（测）**：优化后做功能回归；需要时配合准备压测数据与场景。
- **bug-finder（查）/ bug-fixer（修）**：优化过程中发现的 Bug 交 bug-fixer 定位修复。

重要原则：**没有测量就不要声称优化有效；没有真实数据就不要伪造性能指标。**
